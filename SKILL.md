# High-Taste Technical Writing

## Overview

Write so the reader trusts the mind behind the text, not just the information inside it.

This skill generates technical content with taste, authorial presence, engineering judgment, structural clarity, and disciplined restraint. Its purpose is not to produce louder promotion — it is to produce better writing: precise, credible, structured, readable, and distinct.

## When to Use

Use when the task is to generate:

- technical blog posts
- open-source project introductions
- GitHub project pages
- release posts
- architecture notes
- engineering retrospectives
- product or platform technical explainers
- implementation write-ups

It is especially effective when the writing must balance professionalism and readability, technical depth and accessibility, discoverability and credibility, conversion and restraint.

**It is NOT for:** fabricated depth (never invent value a real project lacks), or pure promotional/ad copy where the goal is to maximize hype at the expense of credibility.

## Priority Order

1. **Taste and authorial quality** — highest priority. The output must feel written by a real technical author with standards, judgment, and proportion.
2. **Clarity, precision, credibility** — the writing must be clear, accurate, and concrete.
3. **Discoverability and conversion** — allowed, but always subordinate to writing quality.

The most important principle: **taste**. Clear judgment, disciplined language, avoidance of cheap emphasis, sensitivity to tone, respect for engineering reality, writing that feels authored rather than assembled. This comes before growth tricks, SEO tricks, and empty enthusiasm.

## Core Requirements

The writing must:

- sound authored, not assembled
- reflect engineering judgment
- stay restrained, even when promotional
- avoid generic AI phrasing
- explain value, not just features
- preserve readability without becoming bland
- guide the reader naturally toward the next action

The writing must not:

- sound like ad copy
- sound like a generic AI summary
- rely on inflated adjectives
- overuse empty praise
- use synthetic enthusiasm
- stuff keywords unnaturally
- force calls to action

## Language Rules

### Avoid AI-template phrasing
Do not use language such as:

- "in today's world"
- "with the rapid development of"
- "this article will take you through"
- "whether you are a beginner or an expert"
- "a powerful and comprehensive solution"
- "hope this helps"

### Prefer mechanisms over adjectives
Do not say something is powerful unless you can explain why. Prefer:

- what it does
- what problem it solves
- why that matters
- what trade-off it reflects
- where it fits

### Allow opinions, but only grounded ones
The writing may disagree, prefer, compare, and judge — but judgment must come from analysis, experience, and technical reasoning, never from performance.

## Recommended Structure

When the user does not specify otherwise, organize the content in this order:

1. real problem or context
2. positioning of the project or solution
3. core strengths explained through value
4. technical design and key decisions
5. usage, deployment, or adoption path
6. summary and natural next-step guidance

## How to Write Strengths

Every major strength must answer:

1. what it is
2. what problem it solves
3. why that problem matters
4. how it differs from common approaches
5. where it is useful
6. what design judgment it reflects

Do not just list features — a feature list is not an argument.

## Tone

Default tone:

- professional
- calm
- precise
- readable
- opinionated without performance
- restrained without dullness

The writing may have warmth, but not sweetness. It may have sharpness, but not vanity.

## SEO and Conversion Rules

### SEO
- use keywords naturally
- cover core technical and scenario terms early
- do not sacrifice readability for discoverability

### Conversion
- lower the reader's barrier to action
- explain who the content is for
- explain why the project is worth attention
- invite action naturally
- never beg for engagement

## Anti-Patterns

The following failure modes are what this skill exists to prevent. Read the table as: symptom → the reality that must guide your writing.

| Symptom | Reality |
|---------|---------|
| Opens with vague industry clichés | Start from a real problem, not praise |
| Overpraises without evidence | Ground every claim |
| Repeats "powerful / robust / comprehensive / efficient" without explanation | Show the mechanism |
| Reads like a feature spreadsheet | Explain value, not features |
| Sounds overexcited | Stay restrained |
| Begs for stars, likes, or engagement | Invite action naturally, never beg |
| Erases all judgment in the name of neutrality | Preserve authorial point of view |
| Optimizes for search at the cost of dignity | Never sacrifice credibility for discoverability |
| Sounds like a brochure or ad copy | The writing has failed — rewrite for taste |

## Quality Checklist

Before finalizing, verify:

- Does it sound like a real author wrote it?
- Does it avoid AI-template phrasing?
- Does it explain problems before selling solutions?
- Does it explain design choices, not just outcomes?
- Does it stay precise and restrained?
- Does it preserve taste under promotional pressure?
- Does it guide action naturally rather than aggressively?

If the result sounds like a brochure, the skill has not been followed correctly.

## Input Requirements

Provide the following context — the more concrete the source material, the better the result:

- **Project or topic** — what it is
- **Problem it solves** — the real friction point
- **Core technical design** — stack or architecture
- **Key strengths** — what to amplify and how it differs
- **Target audience**
- **Target platform** (CSDN / GitHub / blog / etc.)
- **Desired tone**
- **Desired action or conversion goal**
- **Constraints or things to avoid**

Do not ask this skill to invent depth where the project itself has none.

## Output Shape

Deliver the content in this shape (unless the user requests otherwise):

1. Title
2. Opening with a real problem
3. Positioning
4. Core strengths explained through value
5. Technical design and decisions
6. Usage or deployment path
7. Summary
8. Natural next-step guidance
